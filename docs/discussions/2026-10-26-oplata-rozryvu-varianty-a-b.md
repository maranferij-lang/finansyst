# Оплата платежів прямо із застосунку: варіанти А і Б

Нотатки обговорення від 26.10.2026 (команда 3, StartUp Camp від Raiffeisen Bank). Мета документа: щоб з нього можна було зібрати розділ для пітчу, не відновлюючи розмову. Усе, що не підтверджено джерелом, позначено як «не підтверджено».

## Навіщо це нам

Застосунок вже вміє показати касовий розрив і закрити його (овердрафт, гроші з «Резерву», перенесення платежу). Але платити за оренду чи рекламу ФОП після цього мусить окремо: вийти із застосунку, зайти в банк, ввести реквізити, суму, призначення. Віка (24.10) запропонувала замкнути цей ланцюжок: користувач обирає спосіб оплати, сума підтягується сама, платіж проходить, і радар показує, що розриву немає.

Для журі це історія «від попередження до закритого платежу в одному місці». Це відрізняє нас від обліку, який лише показує графіки.

## Що вже є в застосунку (імітація)

- Календар платежів на радарі з кнопкою «Оплатити» (`openBill`): сума підтягується сама, вибір способу оплати (картка ФОП, рахунок ФОП у Райффайзен Банку, LiqPay, WayForPay), оплата імітується, платіж позначається сплаченим.
- Після «Перекинути з Резерву» і після овердрафту застосунок одразу пропонує оплатити платіж, через який був розрив. Після перенесення платежу пропозиції немає: його відкладено навмисно.
- Усі гроші та оплати в прототипі умовні. Реальних зв'язків із банком немає.

## Звідки взяти інформацію про витрати клієнта

| Джерело | Як | Статус |
|---|---|---|
| Виписка рахунку через відкритий банкінг | Банк через API віддає транзакції, ми шукаємо регулярні платежі (той самий отримувач, сума, день) | API Raiffeisen для виписки є (Account API). Для рахунків ФОП не підтверджено |
| Користувач вносить сам | Одноразово: оренда, зарплата, постачальник | Працює без банку |
| Податки | Рахуємо ми з надходжень | Вже є в застосунку |
| Кабінети сервісів (Meta, Prom) | Суми й дати рахунків через їхні API | Припущення, не перевіряли |

## Варіант А: застосунок готує платіж, підписує банк

Приклад: оренда складу 40 000 ₴ за договором, отримувач ФОП Бондар (імена й IBAN вигадані).

1. Користувач один раз вносить отримувача: ім'я, IBAN, призначення «Оплата оренди складу за листопад за договором №12».
2. За два дні до платежу радар показує, що гроші на оренду є (або розрив закрито).
3. Користувач тисне «Оплатити». Застосунок формує платіжну інструкцію: отримувач, IBAN, сума, призначення. Передає її одним із двох способів: файл для імпорту в Raiffeisen Business Online або QR/посилання за стандартом НБУ.
4. Користувач відкриває банк, бачить готовий платіж, перевіряє і підписує як завжди.
5. Платіж з'являється у виписці, застосунок позначає оренду сплаченою.

Плюси: не потрібні API банку. Гроші не проходять через нас. Мінуси: користувач все одно відкриває банк (але нічого не вводить).

Що підтверджено: у Raiffeisen Business Online є імпорт та експорт даних файлом (інструкція банку, 2023). Банк оновлював формати Profix, Bank-Client, BM RS з довшими полями «призначення платежу». Єдиний QR-стандарт НБУ існує, продавці мають приймати QR з 01.11.2025 (постанова НБУ №97).

Що не підтверджено: що саме можна імпортувати (платіжні доручення?), чи потрібен підпис імпортованих платежів, чи вміє RBO для бізнесу оплатити за QR або посиланням.

## Варіант Б: застосунок ініціює платіж через відкритий банкінг

Той самий приклад.

1. Одноразова згода: користувач тисне «Підключити Raiffeisen», потрапляє на сторінку банку, дозволяє читати виписку й ініціювати платежі. Пароль банку застосунок не бачить.
2. Далі так само: радар, «Оплатити».
3. Застосунок надсилає банку платіжну інструкцію через API.
4. Користувач підтверджує саме цей платіж у банку.
5. Банк повідомляє статус, радар одразу показує «розриву немає».

Плюси: найкращий досвід, усе в одному місці. Мінуси: потрібен статус TPP/PISP і доступ до API банку, для ФОП це не підтверджено.

Що підтверджено:
- Положення НБУ про відкритий банкінг (постанова №80) діє з 01.08.2025.
- Raiffeisen Bank Ukraine має сторінку для TPP, Developer Portal і sandbox, Consent API («запитати згоду та ініціювати платежі»), Account API, OAuth.
- На маркетплейсі RBI є «Payments API Bundle – RBUA»: ініціація платежів, статус, пакетні платежі, регулярні платежі за шаблоном, ліміт 1000 викликів на годину.
- Щоб почати, треба зареєструватися на порталі як AISP або PISP і мати сертифікат QWAC.

Що не підтверджено або виявилось проблемою:
- **Для рахунків ФОП і юросіб відкритий банкінг, імовірно, ще не працює.** Представник НБУ казав, що спочатку API відкриють для фізичних осіб, а ФОП і юросіб пізніше. Minfin (червень 2026): специфікації для юросіб ще фіналізуються, банки готові приблизно у серпні–вересні.
- Стартап не може просто підключитись: потрібен статус TPP або партнерство з банком.
- Як клієнт підтверджує платіж і які статуси повертає банк саме в Raiffeisen, не знайдено. Описано загальну схему PSD2.

## Інші способи, які розглядали

- **Платіжний сервіс (LiqPay, WayForPay) для виплати за реквізитами.** Підтвердження, що LiqPay робить виплати на IBAN юросіб через API, не знайшли. Лишаємо як питання до провайдера.
- **Реклама Meta.** Платити реквізитами Meta, найімовірніше, не вийде як у випадку з орендою. Консультанти згадують і картку, і прямий переказ. Реалістична історія: застосунок резервує гроші в конверті «Витрати», нагадує про дату й суму, картка в кабінеті Meta лишається джерелом списання. Окремо потрібне бухгалтерське оформлення для ФОП (ПДВ, документи).

## Помилки, які ми виправили по ходу обговорення

- Спершу було сказано, що ліцензія не потрібна, бо гроші не проходять через нас. Для варіанта Б це неправильно: ініціація платежів це регульована послуга (PISP).
- Спершу було сказано, що відкриті API Raiffeisen для бізнесу немає. Тепер знайшли сторінку для TPP і пакет Payments API для України, але для ФОП це не підтверджено.

## Як говорити на пітчі

Три чесні етапи:
1. **Зараз (прототип):** оплата імітується, щоб показати логіку «розрив, закрили, заплатили».
2. **MVP із банком-партнером (варіант А):** застосунок готує платіж, підписує банк. Гроші ми не тримаємо.
3. **Далі (варіант Б):** ініціація платежу через відкритий банкінг Raiffeisen, коли API для рахунків ФОП будуть доступні.

Можна казати: «У Raiffeisen уже є Payments API з ініціацією платежів, ми погоджуємо з банком доступ для рахунків ФОП».
Не можна казати: «ми підключимось до API завтра» і «ліцензія нам не потрібна».

## Що перевірити далі

1. Спитати наставників Raiffeisen на програмі: чи доступна ініціація платежів для рахунків ФОП уже зараз і коли.
2. Написати на `openbanking@raiffeisen.ua` (і на `open.banking@raiffeisen.ua`, на сторінках банку вказані обидві): чи покривають API рахунки ФОП і бізнес-клієнтів, чи доступна ініціація платежів, що потрібно стартапу-партнеру замість повної ліцензії PISP, який формат файлу приймає RBO для імпорту платежів.
3. Зареєструватися на порталі розробника RBI і прочитати документацію «Payments API Bundle – RBUA» (акаунт створює людина з команди).
4. Перевірити положення №80 і Концепцію відкритого банкінгу на сайті НБУ: типи клієнтів і етапи.
5. Юрист: чи потрібна нам ліцензія в варіанті А.
